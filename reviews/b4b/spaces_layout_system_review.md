# Wavefinity Spaces / Layout System Review

Reviewed repository: `happydadto5/Wavefinity`

Reviewed snapshot: `main` at `07256a02d95371f6974d4608a90edc4ab942af0e`.

Scope reviewed end to end: `organizer_spaces.py`, `organizer_inventory.py`, `organizer_drawer.py`, `organizer_app.py`, B4B inventory semantics, `web/spaces.js`, `web/drawer-model.js`, `web/drawer-panel.js`, `web/drawer-view.js`, welcome/space UI, inventory persistence, auto-layout, spacers, connectors, stacking, and current tests.

This review intentionally omits cosmetic polish, wording tweaks, minor refactors, and low-value feature requests. Items below are limited to correctness problems, architectural risks, or missing capabilities that materially affect whether Spaces can be trusted as the organizing system around Wavefinity.

Priority:

- **P0 — Critical:** produces materially wrong physical/layout results or corrupts the conceptual model; fix before relying on Spaces.
- **P1 — High:** important correctness/data-model/workflow issue; fix in the next serious Spaces pass.
- **P2 — Medium:** significant capability or robustness improvement, but not required to stop current incorrect behavior.

## A. Broken or materially incorrect today

| # | Short description | Full description | Priority |
|---:|---|---|:---:|
| 1 | **Box spaces lose a full 8 mm row and column** | `create_space()` deliberately creates a box space with `clearance: 0.0` because the B4B interior is already the mating child-bin field. Both `organizer_drawer.normalise_drawer()` and `web/drawer-model.js::DL.grid()` then forcibly replace that with the hard-wall drawer minimum of ~0.55 mm. Because grid size is floor-divided, an exact 64 × 48 mm B4B field becomes `floor((64-.55)/8) × floor((48-.55)/8)` = **7 × 5 units / 56 × 40 mm**, instead of the intended 8 × 6 / 64 × 48. This is a direct correctness bug. **Recommendation:** introduce an explicit boundary mode such as `hard_wall` vs `wave_mating`. Box/B4B spaces must use `wave_mating` with zero hard-wall slack. Centralize the rule so Python and JavaScript cannot diverge. Box-space edge shims should also be disabled unless there is a real non-grid residual, because the B4B wall itself is the mating boundary. | **P0** |
| 2 | **A B4B case can be added to its own interior inventory** | Creating a box space sets that folder as the active output and forces `keepLog=true`, then immediately sends the user into B4B design. `generate_b4b_files()` logs generated B4Bs through `log_bin_to_folder()`, which appends a `kind="b4b"` inventory row to the same folder. The result is that the physical case defining the space can appear as an item available to place **inside itself**. **Recommendation:** make the space container a first-class space artifact, not a normal inventory row. Store its generated design/file/revision in `layout.space.case` (or equivalent). Suppress normal inventory logging when the B4B being generated is the current box-space container. A B4B generated as an object for some other space can still be tracked separately if its planner semantics are supported. | **P0** |
| 3 | **B4B inventory rows have the wrong footprint and wrong interlock semantics** | A logged B4B row records `x/y` from the B4B effective child field. Those are **inside capacity dimensions**, not the physical outside footprint or assembled hinge/latch envelope. The B4B module explicitly states that the physical case grows outward and does not promise ordinary external Wavefinity interlock. The Space planner nevertheless passes `kind="b4b"` through `bin_cells()` like an ordinary grid bin, packs it on the Wavefinity lattice, treats it as an ordinary neighbor, and `_connectors()` may calculate standard side connectors against it. This can understate occupied space and prescribe connectors that cannot mate. **Recommendation:** inventory rows need explicit physical/capability metadata: nominal grid footprint, actual outside footprint/envelope, whether each side is Wavefinity-interlocking, stack capability, and connector eligibility. Until that exists, exclude B4B rows from ordinary grid auto-layout and connector generation rather than pretending they are normal bins. | **P0** |
| 4 | **Space size and planner size are two independent sources of truth** | `layout.space` stores the name/kind/x/y/z created by `create_space()`. The first drawer is initially copied from it, but the Drawer/Space panel later allows width, depth, height, clearance and name to be edited independently. Nothing writes those changes back to `layout.space`. The welcome/recent list reads `layout.space`; the planner reads the drawer. A space can therefore claim one size while actually planning another. For box spaces this is especially dangerous because those dimensions describe a physical printed container. **Recommendation:** define one authority. For a one-volume space, `layout.space` should own the physical dimensions and the primary layout surface should derive from it. Editing the primary dimensions must atomically update space metadata. For a box, resizing should be an explicit **Resize box** workflow because it implies redesigning/reprinting the case. | **P1** |
| 5 | **B4B auto-growth can make the saved space disagree with the case that prints** | The box-space metadata and initial layout are committed **before** the B4B design is resolved. B4B may auto-grow dimensions for secure-lid hardware/minimum height or stacking constraints. `SP.designBox()` invokes B4B minimum/effective logic after space creation but never writes the resulting effective child-field dimensions back to the space/layout. This can leave the recent card and planner describing a smaller field than the actual case design or vice versa. **Recommendation:** resolve/validate the B4B effective field first, then commit the authoritative space dimensions; or provide an atomic sync step when the B4B preview changes effective capacity. Persist both requested capacity and effective capacity if the distinction matters, but planner dimensions must always follow the effective child field that will actually print. | **P1** |
| 6 | **Box-space input can round downward below what the user requested** | `web/spaces.js::SP.snap()` uses `Math.round(mm / 8) * 8`. A user asking for a 59 mm inside dimension gets 56 mm. For a container whose setup screen says the user is providing its inside size, silently making the inside smaller is dangerous. **Recommendation:** default to `ceil` for requested minimum inside capacity, or show both adjacent legal sizes and require an explicit choice. The default must never reduce a stated minimum-capacity request without the user knowingly choosing the smaller size. | **P1** |
| 7 | **Existing box spaces do not have a durable “edit/rebuild this case” workflow** | `SP.designBox()` is only automatically invoked immediately after creating a new box space. `SP.openSpace()` merely switches folders and shows a toast. The space does not persist a case-design JSON, design revision, generated-case file reference, or an action that reconstructs the current B4B container. Worse, if the user creates the space but declines the “replace current design” confirmation, the space exists but the case-design workflow is effectively orphaned. **Recommendation:** persist a dedicated container design/reference with every box space and expose **Design/Edit box** from the Spaces screen and Space tab. Opening a box space should always be able to recover the exact current case design. Container generation should update a revision/file pointer in the space metadata. | **P1** |
| 8 | **“No inventory” can mask a real space and is not reliably reversible** | `SP.usePlain()` can mark any folder as no-inventory, including one that already contains a valid space/inventory file. Routing checks the preference marker before the on-disk inventory, so the folder will subsequently behave as “plain” even though the tracked space still exists. `/api/space/open` calls `remember(target)` without `no_inventory=False`, so opening the real space does not clear the marker. This creates two contradictory truths: disk says “space”, preferences say “no inventory”, and the preference wins. **Recommendation:** on-disk space metadata must take precedence. Do not allow a valid space folder to be marked no-inventory without an explicit conversion flow. Opening or creating a tracked space must clear any no-inventory marker for that folder. Ideally no-inventory should be a property of the folder/manifest itself rather than a path-only preference. | **P1** |
| 9 | **Renaming a space folder makes its inventory disappear** | `inventory_path()` derives the inventory filename from the **current folder name** (`<folder name> bins.md`). If the user renames `Garage` to `Workshop`, Wavefinity looks for `Workshop bins.md` even though the existing file is still `Garage bins.md`. The same physical space can therefore appear empty/new after a normal filesystem rename. Recent-space identity is also path-based, with no stable space ID. **Recommendation:** move to a stable inventory/manifest filename independent of the folder basename, e.g. `.wavefinity-space.json` plus `bins.md`, and give every space a UUID. Add migration discovery for a lone legacy `* bins.md` file so renamed existing folders recover automatically rather than appearing blank. | **P1** |
| 10 | **Legacy inventory folders are opened as spaces without a migration step** | `SP.route()` treats `info.exists` as an existing space even when `layout.space` is absent. A legacy inventory file with no layout can then enter the Space tab, where `DL.normaliseLayout()` invents a default 400 × 300 × 60 drawer. That is not the user's measured storage space and can become persisted through normal use/autosave. **Recommendation:** detect `inventory exists && no space metadata`. Run a one-time upgrade flow that asks what physical space it represents and its dimensions, preserves the existing bin rows, and only then writes space metadata/layout. Never silently invent physical dimensions for a migrated inventory. | **P1** |
| 11 | **Auto-layout can report “no room” when a valid arrangement exists** | The auto-layout engine is a set of greedy first-fit strategies (`rows`, `tight`, `columns`, `most`). It sorts items and commits each placement without backtracking. That is fast, but greedy 2D packing can leave an item out even when a different earlier placement would allow everything to fit. The UI presents unplaced results and quick-place failures as if there is definitively no room. For a system intended to decide whether a user needs different bins/spacers, that can drive unnecessary printing. **Recommendation:** keep the greedy pass for instant results, but when items remain unplaced run a bounded backtracking/exact-cover fallback on the remaining region/items. If the bounded search is aborted, say **No fit found** / **best arrangement found**, not an absolute **No room**. | **P1** |

## B. Major system changes I recommend

| # | Short description | Full description | Priority |
|---:|---|---|:---:|
| 12 | **Define the physical “Space” model explicitly** | The UI says one space is “a drawer … or a box,” but the layout model always supports multiple drawers and `+ Drawer` is available even inside a box space. `layout.space` simultaneously stores one x/y/z, which becomes meaningless if the same space contains several drawers. **Recommendation:** choose an explicit model. Best long-term model: a **Space/Project** owns one inventory and contains one or more **Volumes**. Volume kinds can be `drawer`, `box`, etc. A simple Drawer or Box space starts with one volume. A tool chest/cabinet can contain multiple drawer volumes. A box volume should remain exactly one B4B child field. This preserves the useful shared-inventory/multi-drawer capability without pretending one x/y/z describes all of them. If that larger model is not wanted, then restrict each space to one physical volume and remove `+ Drawer` from box/single-drawer spaces. | **P1** |
| 13 | **Introduce a stable space manifest/ID instead of inferring identity from paths** | Space identity currently consists of a folder path, folder-derived filename, and snapshots in preferences. That is fragile under move/rename and makes migrations/conversions harder. **Recommendation:** add a small authoritative manifest containing `space_id`, schema version, display name, space/volume definitions, inventory filename, container design reference, and creation/update metadata. Recent spaces should store `space_id + last_known_path`, allowing Wavefinity to rebind a moved folder. Keep human-readable `bins.md`, but do not make its filename the identity mechanism. | **P1** |
| 14 | **Inventory items need capability metadata, not only `kind` and x/y/z** | The planner assumes nearly every inventory item is a standard Wavefinity grid/interlock object. That is already false for B4B and will become more false as special containers/accessories are added. **Recommendation:** inventory design records should expose planner-facing capabilities such as `grid_footprint`, `physical_envelope`, `rotatable_90`, `wave_interlock_sides`, `connector_eligible`, `stack_mode`, `stack_footprint`, and possibly `source_design`. Planner logic should consume capabilities rather than special-casing `kind`. This prevents the next nonstandard object from silently inheriting invalid bin behavior. | **P1** |
| 15 | **Make boundary behavior a first-class layout property** | Hard drawers need crest clearance from straight walls; B4B child fields intentionally mate to a wavy boundary with no added hard-wall slack. Today the same `clearance` number is forced onto both, which caused finding #1. **Recommendation:** represent boundary behavior explicitly per volume/edge: at minimum `hard_wall` and `wave_mating`. Grid origin, capacity, edge-shim eligibility and collision math should derive from this. This is more robust than sprinkling `if space.kind == "box"` checks and will support future trays/cases with mixed edge behavior. | **P1** |
| 16 | **Move critical layout normalization/validation to one authoritative schema** | The client and server duplicate layout rules (`DL.grid()` vs `drawer_grid()`, clearance floors, snap handling, etc.). `save_inventory()` will persist almost any layout object; most normalization happens only when later reporting/using it. That creates drift risk whenever one side changes. **Recommendation:** add a versioned server-side `normalize_layout()/validate_layout()` that owns physical invariants and migrations. The browser should receive normalized data and use shared values/rules from the API rather than independently reimplementing constants. Reject impossible space/volume states at save time. | **P1** |
| 17 | **Add targeted Spaces regression coverage before extending the feature** | Current tests have a happy-path “new box space is created” check, but they do not assert the cross-module invariants that are currently failing. **Recommendation:** add focused tests for: exact B4B 0-clearance capacity; box container not logging itself as interior inventory; B4B/non-grid capability handling; space↔primary-volume dimension synchronization; B4B auto-growth synchronization; no-inventory conversion/clearing; folder rename migration; legacy inventory migration; box-space reopen/edit-case flow; and multi-volume policy. These are high-value tests because failures otherwise look like plausible layouts rather than crashes. | **P1** |
| 18 | **Use a two-tier optimizer instead of only greedy packing** | This is the architectural form of finding #11. **Recommendation:** Tier 1 remains the current fast heuristic and can generate the familiar alternative arrangements. Tier 2 runs only when Tier 1 leaves normal bins unplaced. Use bounded DFS/backtracking, branch-and-bound, or exact-cover search over candidate grid rectangles. Stop once all items fit or a practical search budget is exhausted. Preserve user locks/keepouts/stack constraints. This provides much higher confidence without slowing the normal easy case. | **P2** |

## C. Important missing options/capabilities

| # | Short description | Full description | Priority |
|---:|---|---|:---:|
| 19 | **Height-aware / 3D keep-outs** | Keep-outs are currently only `x/y/w/d` and therefore reserve the full footprint regardless of height. Real drawers commonly have screw heads, slide rails, handle hardware, lips, or overhangs that only occupy part of Z. Since Wavefinity already reasons about bin and stack height, it should be able to place a short bin under an obstruction that blocks a tall one. **Recommendation:** extend keep-outs with `z0/z1` or a simpler `max_height_here`. Later allow polygon/edge shapes, but height is the important first addition. Auto-layout, drag validation and the 3D Space view must use the same volume rule. | **P2** |
| 20 | **Usage priority and grouping in auto-layout** | Current optimization understands fit, fill, rows/columns and keeping tall bins behind short bins, but not which bins the user reaches for most or which bins belong together. For an organizer, accessibility is often more important than a few percentage points of fill. **Recommendation:** add optional per-bin `access priority` (high/normal/low) and lightweight grouping/tagging. An **Access first** strategy should bias high-priority bins toward the front (and optionally a chosen side), while group constraints/affinity keep related bins near one another. Keep these optional so ordinary users still get one-click auto-layout. | **P2** |
| 21 | **Space-aware constraints while designing a bin** | The bin editor largely operates independently from the active Space. A user can design/generate a bin too wide/deep/tall for the active volume and only discover that later in the Space tab. `Design this spot` is useful but only sends the single largest empty rectangle to the editor. **Recommendation:** when a tracked space is active, make its current volume available to the bin editor. Show live `fits active space` status, enforce or warn on max height, and offer **Design for selected gap/region** from the Space view. The constraint should survive while editing the bin, not be a one-time dimension copy. | **P2** |
| 22 | **Box-space setup needs outside-size feedback and an outside-size mode** | A box space is defined only by desired inside x/y/z, but the real B4B body and its latches/hinges extend beyond that. Someone designing a case to fit a shelf/bag/drawer needs to know the assembled outside envelope before committing. **Recommendation:** during box-space setup, show the derived body outside size and complete assembled envelope from the B4B hardware plan. Add an alternate **Must fit within outside dimensions** mode that solves for the largest legal child field inside a user-specified external envelope. This should reuse authoritative B4B calculations, not approximate wall subtraction in JavaScript. | **P2** |
| 23 | **Cross-space reuse/import of existing bins** | Inventories are isolated by folder. If a physical bin moves from one space to another, or the user wants to reuse a design already tracked elsewhere, the current practical fallback is manual re-entry/generation. **Recommendation:** add **Add existing bin from another space** using the stable space/design IDs proposed above. It should copy/reference the design record and allow the physical quantity to be transferred or duplicated explicitly. This becomes increasingly important once users maintain several drawers/boxes and Spaces becomes the main organizer rather than a single-folder log. | **P2** |

## Recommended implementation order

| # | Short description | Full description | Priority |
|---:|---|---|:---:|
| 1 | **Stop wrong physical results first** | Fix box boundary/zero-clearance capacity, stop self-container logging, and stop B4B rows from being treated as normal grid/interlock bins. These are the current P0 correctness failures. | **P0** |
| 2 | **Establish one authoritative space/volume model** | Decide Space vs Volume semantics, synchronize dimensions, add explicit boundary mode, and make box spaces recoverable/editable. Do this before adding more UI around the current ambiguous model. | **P1** |
| 3 | **Stabilize persistence and migration** | Add stable ID/manifest, migrate legacy inventory and folder-name-derived files, and resolve no-inventory contradictions. | **P1** |
| 4 | **Generalize planner item semantics** | Add capability/physical-envelope metadata and make connectors/stacking/packing consume it. | **P1** |
| 5 | **Make fit decisions more trustworthy** | Add the bounded exact-search fallback and targeted regression tests. | **P1/P2** |
| 6 | **Then add high-value planning options** | Height-aware obstacles, accessibility/grouping, active-space design constraints, outside-size-driven B4B setup, and cross-space reuse can then build on a coherent model. | **P2** |

## Final completeness review

I re-traced the complete data flow after forming the recommendations:

`welcome / folder selection -> space route -> inventory file -> layout.space -> drawer/volume model -> bin generation/logging -> inventory rows -> auto-layout -> placement/report -> spacers/connectors -> save/reopen/recent list`.

The recommendations above cover every material point in that chain that currently changes physical capacity, object identity, saved state, placement eligibility, or fit claims. I intentionally did **not** include smaller UI cleanup, naming consistency, animation/view polish, minor filter options, or code-style improvements.

The most important conclusion is that the **drawer layout engine itself is reasonably substantial**, but the new **Space abstraction is not yet a reliable source of truth around it**. The P0 items are real correctness bugs. The P1 items are the structural work needed before Spaces becomes the durable top-level workflow for Wavefinity.

## Recommended model for implementation

Use a **Top-level coding model with High thinking** for the overall correction. A lot of the diagnosis and target architecture is already specified here, but the work crosses persistence/migration, B4B semantics, browser state, inventory logging, physical layout rules, and optimizer behavior. Individual isolated fixes such as the box-boundary clearance bug could be delegated at Top/Medium once the larger data model is decided, but the first integrated pass should stay Top/High.
