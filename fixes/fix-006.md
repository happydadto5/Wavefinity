# Goal

A Wavefinity Space must survive ordinary filesystem changes such as renaming its folder.

Current behavior ties too much identity to the absolute path and to the folder name:
- the profile/recent state records paths;
- the inventory filename is derived from the current folder name;
- after a Windows folder rename, Wavefinity can lose the recent path and look for a new empty inventory filename.

Replace that with:

1. **Stable Space identity inside the folder**  
   Every typed Space gets a permanent UUID-style `space_id` in its one authoritative `.wavefinity.json`.

2. **Per-user Wavefinity profile registry**  
   Local desktop Wavefinity stores known typed Space IDs, user-visible Space names, Space kinds, and their last known directories in the user's OS profile, not beside the application source.

3. **Folder-name-independent inventory filename**  
   New/current inventory uses one canonical filename:
   `Wavefinity bins.md`

4. **Safe rename recovery**  
   If a known Space path disappears because the folder was renamed in place, Wavefinity uses the registered `space_id` to find the renamed sibling folder and updates the profile path automatically.

5. **Safe manual relocation**  
   If the folder was moved somewhere else, manually opening that folder reads the same `space_id` and updates its registered directory instead of treating it as a new Space.

The folder itself remains the portable source of truth. The profile registry is an index/convenience layer, not the owner of the Space.

# Locked product decisions

## Identity is NOT the path

A path is only the Space's current location.

Do not use any of these as permanent identity:
- absolute path;
- folder name;
- inventory filename;
- Space display name.

Use a stable generated ID.

New typed Space metadata conceptually becomes:

```json
{
  "version": 5,
  "setup_version": 1,
  "folder_mode": "space",
  "space_id": "2b9d7f6d-....",
  "inventory": true,
  "space": {
    "kind": "drawer",
    "name": "Bathroom Vanity",
    "...": "existing type-specific fields"
  },
  "keep_bin_defaults": true,
  "bin_defaults": null
}
```

Use Python `uuid.uuid4()` or the equivalent already imported/available.

The ID is generated once and then preserved through:
- Space name edits;
- folder renames;
- folder moves;
- normal metadata rewrites;
- inventory changes;
- Space dimension edits.

Never generate a new ID merely because the path changed.

## One authoritative JSON in the folder

Continue using:
- `.wavefinity.json`

Do not add a second new JSON identity file.

Legacy `.wavefinity-space.json` may remain readable only as required by the existing migration path, but all current writes go to `.wavefinity.json`.

## Typed Spaces only

The profile Space registry is for real typed Spaces.

Untyped `folder_mode="design"` folders may continue to use the existing recent-folder path list and do not need a fake `space_id`.

Do not turn every ordinary design folder into a Space merely to support this fix.

# Space registry schema

Store the registry inside the per-user `wavefinity_prefs.json` so there is one local profile preferences file, not a second profile database.

Use a top-level key:

```json
"space_registry": {
  "<space_id>": {
    "name": "Bathroom Vanity",
    "kind": "drawer",
    "folder": "C:\\Users\\...\\Bathroom Vanity",
    "last_seen": "2026-09-18T09:30:00-04:00"
  }
},
"active_space_id": "<space_id>"
```

Exact timestamp formatting may use a normal ISO-8601 string.

Registry requirements:
- keyed by `space_id`;
- name comes from authoritative Space metadata, not folder basename;
- kind comes from authoritative Space metadata;
- folder is the current resolved absolute local path;
- last_seen updates when the Space is actually opened/used;
- opening the same ID from a new path updates the path when the prior registered location no longer exists;
- active typed Space stores `active_space_id`;
- opening an untyped design folder clears `active_space_id`.

Keep the existing recent UI behavior, but derive typed-Space recent entries from this registry rather than treating the typed Space path as its identity.

Untyped design recents may remain in `recent_folders`.

Do not store bin inventory or layout in the profile registry.

# Rename recovery

This is required behavior, not optional polish.

Scenario:

```text
C:\Wavefinity\Bathroom Drawer
```

is registered with Space ID `ABC`.

The user closes Wavefinity and renames the folder in Explorer to:

```text
C:\Wavefinity\Master Bath Drawer
```

The next Wavefinity startup must not treat the Space as lost merely because the saved path no longer exists.

## Recovery algorithm

When a registered typed-Space path is missing:

1. Take its recorded parent directory.
2. If that parent still exists, inspect its immediate child directories only.
3. Read only each child's `.wavefinity.json` as needed.
4. Match the exact stored `space_id`.
5. If exactly one child matches:
   - treat it as the same Space;
   - update the registry path;
   - update `output` too if that missing old path was the active output;
   - continue normal startup/open behavior.
6. If zero children match:
   - leave it missing;
   - the user can use Open Existing Space to relocate it manually.
7. If more than one child matches:
   - do not guess;
   - mark/surface a duplicate identity conflict and require manual resolution.

Do not recursively search the entire drive.

Do not identify a renamed Space by matching only its display name.

## Manual relocation

If the old path is missing and the user manually opens a folder elsewhere that contains the same `space_id`:
- update that registry entry to the new path;
- keep the same ID and Space name;
- continue normally.

If the registry points to a different path that still exists and that existing folder contains the same ID, the newly opened second copy is a duplicate identity, not an automatic move.

Do not silently replace the registry path in that case. Surface a clear error such as:

> This folder is a copy of an existing Wavefinity Space and has the same Space identity. The existing Space was left unchanged.

Do not invent a new ID automatically for a copied folder in this fix.

In `organizer_inventory.py`, define one authoritative constant:

```python

```

New and migrated local inventory reads/writes use:

```text
<Wavefinity folder>\Wavefinity bins.md
```

This canonical inventory filename applies to **all inventory-enabled Wavefinity folders**, typed or untyped. Typed Space identity and the inventory filename are separate concerns.

Do not use:

```python

```

as the current filename anymore.

The Markdown title may still use the Space name/folder name for human readability. Only the filesystem filename must become stable.

## Local legacy discovery

A renamed pre-Fix-006 folder may contain:

```text
Master Bath Drawer\
    .wavefinity.json
    Bathroom Drawer bins.md
```

The migration must find that old inventory safely.

When the canonical file does not exist:

1. Check the historical current-name candidate:
   `<current folder name> bins.md`
2. Also look for legacy files matching `* bins.md` in that folder, excluding `Wavefinity bins.md`.
3. If exactly one legacy inventory candidate exists, treat it as the old inventory.
4. On the first allowed write/open migration, rename/move it atomically to `Wavefinity bins.md`.
5. If more than one plausible legacy `* bins.md` file exists, do **not** create a new empty canonical inventory and do not guess. Raise a clear migration error so no inventory is silently split.

Every inventory write path must resolve/migrate the legacy file before writing. The critical failure to prevent is creating:

```text
Bathroom Drawer bins.md   <- real old inventory
Wavefinity bins.md        <- new empty inventory
```

beside it.

Update all local inventory entry points that currently call `inventory_path()`, including load/save/append/create-space paths, so they use one centralized resolver instead of duplicating migration logic.

Keep existing locking and atomic temp-file replacement.

## C. Space-ID validation and ownership

The ID is a canonical UUID string stored **only** at the top level of `.wavefinity.json`.

Local Python validation should be equivalent to:

```python
def _space_id(raw: Any) -> str | None:
    try:
        return str(uuid.UUID(str(raw)))
    except (ValueError, TypeError, AttributeError):
        return None
```

Hosted/browser generation uses `crypto.randomUUID()`.

Rules:

- do not duplicate `space_id` into inventory `layout.space`;
- do not accept a caller-supplied arbitrary ID when creating a new local Space;
- new typed create/configure generates an ID internally;
- every metadata rewrite of an existing typed Space preserves its existing valid ID;
- Edit Space, Set Bin Defaults, inventory-setting writes, and other calls through local `_write_metadata()` or hosted `SP.writeMetadata()` must not drop the ID;
- Design/untyped metadata does not carry `space_id`;
- metadata must be successfully persisted before the profile registry is updated.

For local code, make `_write_metadata()` the preservation choke point rather than patching every route separately. It should read/preserve the existing valid ID for a typed Space and generate one only for a legitimate new/v4-upgrade write. Existing v5 typed metadata with no valid ID must error as above.

For hosted code, `SP.writeMetadata()` must do the equivalent preservation. The current Fix-004 implementation rebuilds the metadata object from scratch, so this is mandatory.

## E. Startup recovery order

For local startup, `active_space_id` becomes stronger identity than the remembered path.

Resolution order:

1. If `active_space_id` names a registry entry, validate its recorded folder by reading that folder's `.wavefinity.json` and confirming the same ID.
2. If valid, use that path and keep `output` synchronized to it.
3. If the recorded location is missing or no longer contains that ID, run same-parent ID recovery.
4. If exactly one sibling contains the ID, update registry + `output` and continue.
5. If recovery fails, fall back to Welcome/Home; manual Open Existing Space can relocate it.
6. If no `active_space_id`, preserve the existing Fix-004 `output` startup behavior for untyped/legacy state.

A registry path is not valid merely because the directory exists. It must contain the expected ID.

If the old directory exists but now contains a different Space/no matching ID, treat that registry location as stale and attempt recovery; do not classify it as the registered Space.

An old v4 Space that was renamed **before it ever received a Fix-006 ID** cannot be auto-recovered by identity. Do not guess by name. The user must Open Existing Space once; from then on the assigned ID makes future renames recoverable.

## F. Duplicate-ID detection must distinguish stale paths from real copies

A duplicate conflict exists only when two distinct accessible folders both contain the same valid `space_id`.

When manually opening Space ID `X` at a new path:

- registered old path missing -> adopt new path;
- registered old path exists but does not contain `X` -> registered path is stale; adopt new path;
- registered old path resolves to the same folder under case/path normalization -> same Space, no conflict;
- registered old path is distinct and also contains `X` -> duplicate-copy conflict; do not change either folder or the registry.

Use the existing path-normalization behavior (`_same`/equivalent) so Windows case differences do not create false duplicates.

Same-parent recovery should inspect immediate child directories only, never recurse across the drive.

## G. Registry mutation and recent-list rules

`space_registry` is a durable registry, not merely the eight-item Recent list.

- never truncate `space_registry` to `MAX_RECENT`;
- `last_seen` changes only when the Space is actually opened/used, not merely inspected;
- when an accessible registered Space is read, refresh cached `name` and `kind` from folder metadata;
- folder metadata wins over cached registry name/kind;
- use an ISO timestamp; UTC is preferred;
- protect load-modify-write registry operations with the existing `PREFERENCES_LOCK` so concurrent threaded requests cannot overwrite each other's registry changes.

## H. Exact local inventory resolver

Do not make `inventory_path()` blindly return only the canonical filename, because Fix-004 read-only inspection must still be able to read an old renamed inventory before migration.

Use one resolver with behavior equivalent to:

```python
INVENTORY_FILENAME = "Wavefinity bins.md"

def resolve_inventory_path(output_dir: Path | str, *, migrate: bool) -> Path:
    folder = Path(output_dir).expanduser().resolve()
    canonical = folder / INVENTORY_FILENAME

    legacy = []
    preferred = folder / f"{folder.name} bins.md"
    if preferred.is_file():
        legacy.append(preferred)
    for path in folder.glob("* bins.md"):
        if path.name != INVENTORY_FILENAME and path.is_file() and path not in legacy:
            legacy.append(path)

    if canonical.is_file():
        if legacy:
            differing = [p for p in legacy if p.read_bytes() != canonical.read_bytes()]
            if differing:
                raise InventoryMigrationError(
                    "Multiple Wavefinity inventory files were found; nothing was changed."
                )
        return canonical

    if not legacy:
        return canonical
    if len(legacy) != 1:
        raise InventoryMigrationError(
            "Multiple Wavefinity inventory files were found; nothing was changed."
        )

    source = legacy[0]
    if not migrate:
        return source

    source.replace(canonical)
    return canonical
```

Exact exception naming may follow project style.

Call it:
- `load_inventory(...)` with `migrate=False`;
- `save_inventory(...)`, `append_bin(...)`, and `configure_space(...)` with `migrate=True`;
- any other local runtime inventory writer with `migrate=True`.

Keep the resolver and rename under `INVENTORY_LOCK`.

If canonical + an identical legacy file coexist, canonical may be used safely; do not merge rows. Cleanup of an identical redundant legacy file is optional and must occur only on an explicit write/open migration, never during read-only inspect.

Do not touch historical `.bak` files.
