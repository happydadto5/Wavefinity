# Goal

Make hosted/Render first-run onboarding behave predictably and immediately. This one fix covers four related problems discovered together:

1. stale Drawer data can bypass the three Space-type cards;
2. Welcome can appear 15–20+ seconds after the Design screen because onboarding waits for the first 3D preview;
3. Drawer / Surface / Portable Storage card images 404 on Render;
4. on a browser without writable-directory support, **Choose Folder & Create** silently downloads `Wavefinity bins.md` instead of choosing a folder and creating a persistent Space.

Do not redesign unrelated Space behavior.

# A. Correct Space-type routing

## Reported behavior

A folder that does not have a currently committed typed Space can be routed straight into Drawer setup. The current code can treat old Drawer data embedded in the inventory/layout as an authoritative current Space.

Relevant code:
- `organizer_spaces._folder_state()`
- `SP.inspectHosted()`
- `SP.enterSetupFor()`

## Locked behavior

- Fully configured current typed Spaces resume normally.
- Explicitly typed older Spaces being migrated may keep their known type preselected/prefilled.
- A current ordinary `folder_mode="design"` folder is not converted into a typed Space merely because inventory/layout still contains old Drawer/Space data.
- When no authoritative committed Space type exists, setup must show the existing three cards:
  - Drawer
  - Surface
  - Portable Storage
- Safe old values may be retained only as a matching-type prefill candidate after the user chooses a type.
- Never delete inventory/layout data merely to classify setup.

## Implementation

### `organizer_spaces.py`

In `_folder_state()`, a current/onboarded design marker must outrank stale inventory/layout Space data.

Today `design_result` is built but `explicit_space` is checked before it is returned. For current completed design metadata, return the design result before inventory/legacy inference.

Equivalent narrow rule:

```python
if metadata.get("folder_mode") == "design":
    explicit = _explicit_inventory(metadata)
    enabled = explicit if explicit is not None else _default_inventory(folder, prefs)
    design_result = ("design", None, enabled, False, None, needs_setup)
    if not needs_setup:
        return design_result
```

Preserve migration behavior for genuinely older metadata that still needs setup.

### `web/spaces.js`

Mirror the same precedence in `SP.inspectHosted()`.

Use an explicit condition such as:

```js
const currentDesignAuthoritative =
    currentState.status === "design" && !currentState.needsMigration;
```

Handle that before `genuineInventorySpace` / legacy Space fallback.

Track provenance of any candidate Space, e.g. `space_source`:
- `metadata`
- `legacy_metadata`
- `inventory_layout`
- `inventory_inferred`
- `null`

Do not infer authority from `kind` alone.

Change `SP.enterSetupFor()` so direct `SP.showSetup(kind, data.space)` occurs only for an authoritative typed source. Inventory/layout-only or inferred candidates must show `SP.showTypeCards()`.

Add a transient candidate such as `SP.setupPrefillSpace`:
- retained while moving cards -> matching type form -> Back within the same migration flow;
- only passed to `SP.showSetup()` when the selected card matches the candidate type;
- legacy `box` maps to `portable`;
- cleared by `SP.clearSetupContext()` and every genuinely new Create flow;
- never leaks into a later unrelated Create.

Update stale comments that claim inventory `layout.space` is always authoritative.

# B. Show Welcome before initial 3D preview

## Root cause

`web/app.js:init()` currently does:

```js
await refreshPreview();
state.ready = true;
window.dispatchEvent(new Event("wavefinity:ready"));
```

`web/spaces.js` does not call `SP.launch()` until `wavefinity:ready`.

Therefore the ordinary Design UI renders first and the Welcome/Resume decision is artificially blocked behind the first server-side 3D preview. On slower hosted/free compute this can take many seconds.

## Required behavior

- Once catalog/runtime data and DOM wiring needed by Spaces are ready, start Space onboarding immediately.
- Do **not** wait for the first preview request to finish before deciding whether Welcome / Resume / setup should appear.
- First-run users should not stare at the normal Design screen while onboarding is still pending.
- Existing typed Space Resume remains correct.
- Existing preview generation still occurs; this is a startup sequencing change, not removal of the preview.

## Implementation

In `web/app.js:init()`, move the readiness handoff before the initial preview:

```js
clearDraftSelection();

state.ready = true;
window.dispatchEvent(new Event("wavefinity:ready"));

await refreshPreview();
```

Before using exactly that patch, verify there is no startup race with a Space flow that itself changes `state.design`. If necessary, use a small distinct event/state such as `wavefinity:spaces-ready`, but keep the principle: **Space startup must not depend on completion of the initial default-bin preview.**

If a race exists, serialize only the design-changing branch; do not restore the blanket preview-before-Welcome delay.

A lightweight startup veil is acceptable only if needed to prevent a brief Design-screen flash, but the preferred fix is correct event sequencing, not a cosmetic delay.

Render Free cold-start time itself is outside Wavefinity, but Wavefinity must not add another avoidable preview delay after the page is available.

# C. Serve the three card images on Render

## Root cause

`web/index.html` correctly references:

- `/images/Drawer.png`
- `/images/Vanity.png`
- `/images/B4B.png`

The files exist in repository root `/images/`.

But `wavefinity_web.py` serves normal static requests only from:

```python
WEB_ROOT = APP_DIR / "web"
...
candidate = (WEB_ROOT / relative).resolve()
```

So `/images/*.png` is looked up as `web/images/*.png`, which does not exist, and Render returns 404.

## Required implementation

Keep one authoritative copy of the image files in the existing root `images/` folder. Do not duplicate assets solely to work around routing.

Add a narrow static route in `WavefinityHandler.do_GET()` for `/images/` that resolves only inside:

```python
IMAGE_ROOT = APP_DIR / "images"
```

Requirements:
- `/images/Drawer.png`, `/images/Vanity.png`, `/images/B4B.png` return 200;
- preserve path-containment protection against `..` traversal;
- retain correct MIME types and the same security/cache headers used for normal static files where practical;
- do not expose arbitrary repository files.

Prefer a tiny shared static-file sender/helper if that removes duplicated header logic cleanly.

Do not change the visible card markup or approved images.

# D. Do not turn “Choose Folder & Create” into a download

## Root cause

Hosted `SP.pickFolder()` currently does:

```js
if (!window.WFFileSystem?.supportsDirectoryPicker()) {
  return { handle: null, name: "Browser downloads", fallback: true };
}
```

Later, the Space create path calls `WFFileSystem.writeText(folder.handle, ...)`. With `handle === null`, `writeBlob()` deliberately downloads the file.

This makes a persistent-Space action silently degrade into a completely different operation.

The key browser capability is `window.showDirectoryPicker()`. Chromium-based desktop browsers support it; browsers such as Firefox do not. This is browser capability, not Linux-vs-Windows behavior.

## Locked behavior

- **Choose Folder & Create** must either obtain a real writable directory handle or not create the Space.
- It must never silently create a download-only pseudo-folder.
- Unsupported browsers may still use normal design/download functionality, but cannot pretend to have persistent local folder-backed Spaces.
- The existing Unsupported/Folder Access dialog is the right UX destination.
- No server-side Render folder may be substituted for the user's local folder.
- No fake path strings.
- No attempt to bypass browser security.

## Implementation

Change `SP.pickFolder()` so hosted folder-selection workflows do **not** fabricate:

```js
{ handle: null, name: "Browser downloads", fallback: true }
```

For an unsupported browser:
1. call/show the existing `SP.showFolderAccessNeeded()` UI;
2. return `null`;
3. leave the current setup values intact so the user does not lose measurements/name;
4. do not call `create-text`, `configure-text`, `writeMetadata`, or `writeText`;
5. do not trigger a download.

Apply this to:
- Create typed Space;
- Open Existing Space/folder workflows;
- Choose another folder;
- any other action whose wording promises a persistent folder.

Normal non-Space downloadable design behavior remains available without folder access.

Update unsupported-browser copy so it does not imply Windows-only support. Use wording similar to:

> Persistent Inventory and Spaces need a desktop browser with writable folder access, such as Chrome, Chromium, or Edge. You can still design and download parts in this browser.

Do not hard-code OS detection; capability detection is authoritative.

If `useHostedFolder()` still retains a download-only fallback for some explicitly download-oriented flow, it must no longer be reachable from a button that says Choose/Open Folder or Create Space.
