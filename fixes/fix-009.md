## Reported bug

On launch, a folder that does not have a currently committed typed Space can be routed straight into the Drawer setup form instead of showing the three Space-type cards (Drawer / Surface / Portable Storage with their images).

The current code can treat a stale or legacy drawer definition embedded in the inventory/layout as if it were an authoritative current Space. In particular:

- local `organizer_spaces._folder_state()` reads `layout.space` before it finally returns a current `folder_mode="design"` result, so an old drawer layout can override an ordinary design-folder classification;
- hosted `SP.inspectHosted()` similarly lets `genuineInventorySpace` outrank current design metadata;
- `SP.enterSetupFor()` then sees a recognized `data.space.kind` and calls `SP.showSetup(kind, data.space)`, which bypasses the three type cards.

This violates the intended onboarding rule: **if there is no currently committed Space type, choosing/entering Space setup must show the three type cards.** A stale/inferred drawer may be used as a safe prefill suggestion after Drawer is chosen, but it must not silently choose Drawer for the user.

## Locked behavior

1. A fully configured current typed Space continues to resume normally.
2. An explicitly typed older Space being migrated may keep its known type preselected/prefilled.
3. A current ordinary design folder is not converted into a typed Space merely because its inventory/layout still contains old drawer/space data.
4. If setup is required but no authoritative typed Space exists, show the three cards:
   - Drawer
   - Surface
   - Portable Storage
   using the existing card images and existing `space-type-cards` UI.
5. If old inventory data contains a valid Space definition, preserve it only as a **prefill candidate**. If the user chooses the matching card, reuse safe name/dimensions. If the user chooses another type, do not cross-prefill incompatible fields.
6. Do not delete or rewrite inventory/layout data merely to decide which setup screen to show.
7. Keep local and hosted/browser-folder classification behavior equivalent.

## Required implementation

### 1. `organizer_spaces.py` — restore metadata precedence

In `_folder_state()`, current completed design metadata must outrank stale inventory/layout Space data.

Today the function builds `design_result` but checks `explicit_space` before returning it. Change the precedence so that a valid current/onboarded design marker is authoritative before inventory/legacy Space inference.

Use the existing `needs_setup` calculation. The narrow intended rule is equivalent to:

```python
if metadata.get("folder_mode") == "design":
    explicit = _explicit_inventory(metadata)
    enabled = explicit if explicit is not None else _default_inventory(folder, prefs)
    design_result = ("design", None, enabled, False, None, needs_setup)

    # Current/onboarded design metadata is authoritative. Old inventory
    # layout.space must not silently convert it into a typed Space.
    if not needs_setup:
        return design_result
```

Preserve the existing migration behavior for genuinely old metadata that still needs the one-time setup pass.

Do not remove support for true explicit typed metadata, legacy typed metadata, legacy `box`, or data-preserving migration.

### 2. `web/spaces.js` — mirror that precedence in `SP.inspectHosted()`

Hosted/browser-folder classification must make the same distinction.

Add a clear condition such as:

```js
const currentDesignAuthoritative =
    currentState.status === "design" && !currentState.needsMigration;
```

A current authoritative design marker must be handled before `genuineInventorySpace` / legacy Space fallback.

Also ensure `legacyMatters` does not make stale legacy metadata outrank an authoritative current design marker.

Keep the existing inventory-enabled default behavior intact.

### 3. Track whether a setup kind is authoritative or only inferred

The setup router needs provenance so it can distinguish:

- current typed metadata;
- explicit legacy typed metadata;
- inventory/layout-only Space data;
- layout-inferred Drawer data;
- no Space data.

Use a small field returned by local `describe()` and hosted `SP.inspectHosted()`, for example `space_source` with stable values such as:

- `"metadata"`
- `"legacy_metadata"`
- `"inventory_layout"`
- `"inventory_inferred"`
- `null`

Do not infer authority from the kind string alone.

For local mode, derive the source read-only from the same files/layout already used for classification. Avoid a second independent Space parser.

For hosted mode, the data is already available inside `SP.inspectHosted()` as `currentState`, `legacyState`, `inventorySpace`, and `inventorySpaceInferred`.

### 4. `SP.enterSetupFor()` — only skip cards for an authoritative typed Space

Current behavior:

```js
if (data.space && ["drawer", "surface", "box", "portable"].includes(data.space.kind)) {
    const kind = data.space.kind === "box" ? "portable" : data.space.kind;
    SP.showSetup(kind, data.space);
}
```

Change this so direct form entry happens only when the Space kind came from an authoritative typed source (current typed metadata or explicit legacy typed metadata).

If the only Space information is inventory/layout-derived or inferred, keep `SP.configureData = folder` but show `SP.showTypeCards()` instead.

### 5. Preserve inferred values only as matching-type prefill

Add one small transient setup field, e.g. `SP.setupPrefillSpace`.

- Set it when `SP.enterSetupFor()` receives a safe inferred/legacy candidate but must show the cards.
- Clear it in `SP.clearSetupContext()`.
- When a type card is clicked, map legacy `box` to `portable`.
- Pass the prefill to `SP.showSetup()` only when the selected card matches the candidate type.
- Selecting a different card starts that type cleanly.
- Back from the form to the cards may keep the candidate during this same setup flow.
- Starting a genuinely new Space via `SP.beginCreateNew()` must clear the candidate.

Do not let this transient prefill leak into a later unrelated Create flow.

### 6. Comments/copy

Update comments in `organizer_spaces.py` and `web/spaces.js` that currently say an explicit inventory `layout.space` is always authoritative. It is only authoritative as a migration/prefill source when no newer committed folder classification overrides it.

No image, card layout, or visible wording change is required for this fix.
