# Goal

Make first-run/onboarding behavior deterministic and safe on local Wavefinity and on the hosted Render build.

This single fix covers four observed problems:

1. stale/inventory-derived Drawer information can bypass the three Space-type cards;
2. Welcome can appear 15–20+ seconds after the ordinary Design UI because Space startup waits for the first 3D preview;
3. Drawer / Surface / Portable Storage card images 404 on Render;
4. on browsers without writable-directory support, **Choose Folder & Create** silently becomes a download of `Wavefinity bins.md` instead of creating a persistent folder-backed Space.

The implementation must be **capability-driven, not OS-name-driven**. macOS, Linux, Android, and iOS browsers do not expose identical file APIs.

Do not redesign unrelated Space or Design behavior.

# Cross-platform contract

Use runtime capability checks. Do not branch on user-agent strings.

## macOS

- Chromium-family browsers that expose a writable `showDirectoryPicker()` path may create/open persistent Spaces.
- Safari currently does not provide Wavefinity's required writable-directory picker path; it must receive the explicit folder-access explanation.
- Normal design + downloaded output must continue to work in either case.

## Linux

- Chromium/Chrome/Edge-style browsers that expose writable directory handles may create/open persistent Spaces.
- Firefox-style browsers that do not expose `showDirectoryPicker()` must **not** silently download `Wavefinity bins.md`; show the explicit folder-access explanation instead.
- Sandboxed packaging/portal behavior must be handled by the browser API/permission result, not OS detection.

## Android

- Do not assume support from the OS name or browser brand.
- If the running browser exposes the required picker and grants a real writable directory handle, use it.
- If the picker is absent, denied, or does not provide the required directory-handle methods, persistent Space actions must stop cleanly.
- Design/download mode must remain available.

## iOS / iPadOS

- Do not try to emulate a writable Space folder with downloads, `webkitdirectory`, server storage, or fake paths.
- If no writable `showDirectoryPicker()` capability exists, persistent Inventory/Spaces are unavailable in that browser session and the user gets the explicit explanation.
- Design/download mode remains available.

# A. Correct Space-type authority and routing

## Root cause

The current local and hosted classifiers can allow old inventory/layout Space data to act as though it were the currently committed Space type:

- local: `organizer_spaces._folder_state()`;
- hosted: `SP.inspectHosted()`;
- UI: `SP.enterSetupFor()` skips the cards whenever `data.space.kind` is recognized.

The UI therefore lacks the provenance needed to distinguish a committed typed Space from an inventory-only candidate.

## Locked behavior

1. Current configured typed Space -> resume normally.
2. Explicit legacy typed metadata being migrated -> may preselect/prefill that known type.
3. Current completed `folder_mode="design"` metadata -> remains Design even if inventory/layout still contains an old Drawer/Space definition.
4. No authoritative committed Space type -> show the three existing cards:
   - Drawer
   - Surface
   - Portable Storage
5. Inventory/layout-only Space values may be kept only as a **matching-type prefill candidate** after the person explicitly chooses that type.
6. Choosing a different type must never inherit incompatible dimensions.
7. Do not delete/rewrite inventory just to classify the setup screen.
8. Local and hosted classification must report the same authority concept.

## C1. `wavefinity_web.py`

Extract the current normal-static response block into a handler helper equivalent to:

```python
def _send_static_file(self, root: Path, relative: str) -> None:
    resolved_root = root.resolve()
    candidate = (resolved_root / relative).resolve()
    try:
        candidate.relative_to(resolved_root)
    except ValueError:
        self.send_error(HTTPStatus.NOT_FOUND)
        return
    if not candidate.is_file():
        self.send_error(HTTPStatus.NOT_FOUND)
        return

    body = candidate.read_bytes()
    content_type = mimetypes.guess_type(candidate.name)[0] or "application/octet-stream"
    self.send_response(HTTPStatus.OK)
    self.send_header("Content-Type", content_type)
    self.send_header("Content-Length", str(len(body)))
    self.send_header("Cache-Control", "no-cache")
    self.send_header("X-Content-Type-Options", "nosniff")
    self.send_header("Referrer-Policy", "no-referrer")
    self.send_header("Cross-Origin-Resource-Policy", "same-origin")
    self.send_header(
        "Content-Security-Policy",
        "default-src 'self'; script-src 'self'; style-src 'self'; "
        "connect-src 'self'; img-src 'self' data: blob:; object-src 'none'; "
        "base-uri 'none'; frame-ancestors 'none'",
    )
    self.end_headers()
    self.wfile.write(body)
```

# D. Persistent Space actions must never become downloads

## Root cause

Hosted `SP.pickFolder()` currently fabricates this when the picker API is absent:

```js
{ handle: null, name: "Browser downloads", fallback: true }
```

Persistent Space code later passes the null handle to `WFFileSystem.writeText()`, whose shared `writeBlob()` intentionally downloads when no handle exists. That download fallback is valid for generated part files, but invalid for “Choose Folder & Create”.

**Do not remove the normal generated-file download fallback from `writeBlob()`.**  
Instead make it impossible for persistent folder/Space workflows to reach it without a real handle.

## D1. `web/browser-files.js` — capability + permission API

Replace the picker/permission portion with this behavior:

```js
const supportsDirectoryPicker = () =>
  window.isSecureContext &&
  typeof window.showDirectoryPicker === "function";

const queryReadWritePermission = async handle => {
  if (!handle || typeof handle.queryPermission !== "function") return false;
  try {
    return (await handle.queryPermission({ mode: "readwrite" })) === "granted";
  } catch (_error) {
    return false;
  }
};

const requestReadWritePermission = async handle => {
  if (!handle) return false;
  if (await queryReadWritePermission(handle)) return true;
  if (typeof handle.requestPermission !== "function") return false;
  try {
    return (await handle.requestPermission({ mode: "readwrite" })) === "granted";
  } catch (error) {
    if (["SecurityError", "NotAllowedError"].includes(error?.name)) return false;
    throw error;
  }
};

const pickDirectory = async () => {
  if (!supportsDirectoryPicker()) {
    return { status: "unsupported", handle: null };
  }
  try {
    const handle = await window.showDirectoryPicker({ mode: "readwrite" });
    if (
      !handle ||
      handle.kind !== "directory" ||
      typeof handle.getFileHandle !== "function"
    ) {
      return { status: "unsupported", handle: null };
    }
    if (!(await requestReadWritePermission(handle))) {
      return { status: "denied", handle: null };
    }
    return { status: "ok", handle };
  } catch (error) {
    if (error?.name === "AbortError") {
      return { status: "cancelled", handle: null };
    }
    if (["SecurityError", "NotAllowedError"].includes(error?.name)) {
      return { status: "denied", handle: null };
    }
    throw error;
  }
};
```

Export `queryReadWritePermission` as well.

### Permission loss must fail closed

Current read helpers can return “missing” values when a real handle exists but permission is unavailable. That can make an existing folder look empty/new.

For `readText()`, `fileExists()`, and `listFilenames()`:

- keep their existing no-handle behavior only where it is meaningful;
- if a **real handle exists** but `requestReadWritePermission(handle)` is false, throw a clear error instead of returning `null`, `false`, or `[]`.

Example:

```js
if (!(await requestReadWritePermission(handle))) {
  throw new Error(
    "Wavefinity no longer has permission to read and write that folder. Choose the folder again and allow access."
  );
}
```

`removeFile()` already follows the fail-closed pattern.

Keep this exact invariant in `writeBlob()`:

```js
if (!handle) return download(blob, filename);
```

because ordinary generated-file downloads depend on it.

# E. Keep ordinary download mode intact

The shared browser filesystem layer serves two different purposes:

1. persistent selected-folder writes for Inventory/Spaces;
2. deliberate browser downloads for generated design files.

Fix 009 changes only #1.

`web/app.js:saveGeneratedFiles()` currently calls:

```js
await WFFileSystem.writeBlob(folder?.handle, file.name, await response.blob());
```

When there is no selected folder, the null handle intentionally downloads the generated file. **Preserve this.**

Do not globally make `writeBlob(null, ...)` throw.

The safety line is: Space/inventory code must require a real handle before it ever calls `writeText()` or metadata/inventory logic.
